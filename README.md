# dotfiles

My personal configuration for a WSL2 (Ubuntu) + WezTerm setup on Windows.

## What's inside

| Config | Path | Symlinked to | Notes |
| --- | --- | --- | --- |
| **zsh** | `zsh/.zshrc`, `zsh/.zshenv` | `~/.zshrc`, `~/.zshenv` | Login shell. History, prompt, completion, conda, nvm, fzf. `.zshenv` holds what non-interactive shells need on PATH too (the rust and .NET toolchains). |
| **bash** | `bash/.bashrc` | `~/.bashrc` | Kept as a fallback shell. |

## Configs

### zsh (`zsh/.zshrc`)
The primary interactive shell. Ported from the old `.bashrc`:
- History with dedup + shared history across shells.
- Coloured `user@host:cwd` prompt and xterm title.
- `compinit` completion (with `bashcompinit` so nvm's completion loads).
- `ls`/`grep` colour aliases plus `ll`/`la`/`l`.
- conda (via the `shell.zsh` hook), ssh-agent bootstrap, nvm, and fzf.
- [zoxide](https://github.com/ajeetdsouza/zoxide) as a smarter `cd`: `z foo` jumps to the most-used directory matching `foo`, `zi` picks one interactively through fzf. The init is guarded on the binary being present, so the shell still starts cleanly without it.
- Extra aliases can be dropped in `~/.zsh_aliases`.

### git (`git/`)
- `.gitconfig` — identity, `main` as the default branch, `vim` editor, and aliases (`st`, `co`, `br`, `ci`, `lg`, `last`, `unstage`).
- `.gitignore_global` — OS/editor junk ignored across every repo (wired up via `core.excludesfile`).

### nvim (`nvim/`)
- **lazy.nvim** self-bootstraps on first launch; `lazy-lock.json` pins plugin versions so every machine installs the same commits.
- **harpoon** — `<leader>a` add, `<leader>h` menu, `<leader>1..4` jump.
- **flash** — [flash.nvim](https://github.com/folke/flash.nvim). `s` then two characters labels every match on screen; press the label to teleport. Covers the gap between `f`/`t` (this line only) and telescope (another file) — the range where `hjkl`-mashing actually happens. Works in visual and operator-pending too, so `ds..` deletes to a label. Shadows the built-in `s` (substitute character); `cl` is the same thing.
- **telescope** — `<leader>ff` files, `<leader>fg` grep, `<leader>fb` buffers, `<leader>fh` help, `<leader>fe` file browser.
  - [telescope-ui-select](https://github.com/nvim-telescope/telescope-ui-select.nvim) routes `vim.ui.select()` through telescope, so *every* menu nvim raises is a fuzzy-filterable dropdown instead of a numbered `inputlist` in the command area — LSP code actions (`<leader>ca`), the Makefile target pickers (`<leader>mm`, `<leader>dM`), and anything added later, since they all go through the same hook.
- **Worktrees** — `<leader>fw` picks a git worktree, `cd`s into it and drops you straight into `find_files` there (`<Esc>` if the `cd` was all you wanted). No plugin: `vim.ui.select` goes through telescope-ui-select, so it's a fuzzy picker for free — the same trick the Makefile pickers use.
  - It exists because of a specific trap with agent worktrees. Claude puts them at `<repo>/.claude/worktrees/<name>` and excludes that path in `.git/info/exclude`, so `<leader>ff` **cannot see into one from the main checkout** — `fd` honours the exclude, and the directory is hidden besides. That exclusion is correct: a worktree is a second full checkout, so without it every file in the project would appear once per worktree in every search. The fix therefore isn't a flag on the finder, it's being in the worktree in the first place.
  - The main checkout shows its full path and everything else is shown relative to it, because an agent worktree's identity is `.claude/worktrees/<name>` and repeating the repo root in front of every row buries that past the edge of the popup. Locked worktrees are marked.
- **neo-tree** — [neo-tree.nvim](https://github.com/nvim-neo-tree/neo-tree.nvim), the sidebar tree. `<leader>e` toggles it and *reveals* the current file, expanding the directories above it, so it always answers "where am I". Complements telescope rather than replacing it: telescope finds a file you can name, neo-tree shows you the shape of a directory you can't. Inside it, `<Space>` expands/collapses, `<CR>` opens, `a`/`d`/`r` add/delete/rename, `C`/`z` collapse this node / everything, and `?` lists the full keymap. Gitignored files are hidden, dotfiles are not; `H` toggles both. `motions.lua` carries the complete set.
- **gitsigns** — [gitsigns.nvim](https://github.com/lewis6991/gitsigns.nvim), the *inline* half of "show me the diff": what changed on this line, answered without leaving the line. (The other half — what changed across a branch — wants a file list and a two-pane view, and is a different tool.) It earns its place because these files change underneath the editor: a claude in the next tmux window, a formatter, a rebase. The gutter turns "which lines did something else touch, and do I agree" into a glance rather than a `git diff` in another pane.
  - Prefix is `<leader>g`, not gitsigns' suggested `<leader>h` — that's harpoon's quick menu here, and harpoon gets used far more often than any hunk operation.
  - **Moving** — `]c`/`[c` next/previous hunk. Inside a real diff split they fall through to vim's own diff-mode motions, which is what they have to mean there.
  - **Reading** — `<leader>gp` preview the hunk *inline* (the diff opens under the line, no float), `<leader>gP` in a float instead, `<leader>gb` full blame for this line, `<leader>gd` diff this file against the index, `<leader>gD` against the last commit, `<leader>gq` every hunk in the buffer to the quickfix list (`<leader>gQ` for the whole repo).
  - **Staging** — `<leader>gs` stage the hunk, `<leader>gr` discard it, `<leader>gS`/`<leader>gR` the whole buffer. In visual mode `gs`/`gr` take *part* of a hunk, down to a single line. There's no unstage key: `<leader>gs` on an already-staged hunk unstages it. A buffer with three unrelated fixes becomes three commits without a single `git add -p`.
  - **`ih` is a text object** — the part that makes this feel like vim rather than a git client. `dih` deletes the hunk under the cursor, `vih` selects it, `=ih` reindents just it.
  - **Inline blame is on** — author, date and commit summary as virtual text at end of line, 400ms behind the cursor. Off in gitsigns by default, and the single most useful thing it does: "who wrote this and why" answered continuously instead of on request. `<leader>gB` toggles it when it's in the way.
  - **The signs** — `┃` added or changed lines, `▁`/`▔` a deletion above/below, `~` a line changed *and* lines deleted, and `┆` (dashed) for a file git has never seen at all. Solid vs dashed is "new lines" vs "new file".
  - **Untracked files are signed too** (`attach_to_untracked`, off upstream). Gitsigns finds them with `ls-files --others --exclude-standard`, and `--exclude-standard` means anything `.gitignore` covers returns nothing — so build output and venvs stay dark and only genuinely-new files light up. Worth having because of how files get written here: a claude in the next tmux window creating one is exactly the case where "this exists but git has never heard of it" needs to be visible *before* the commit that misses it.
  - **`signcolumn = 'yes'`** is set alongside it. On nvim's default `auto` the column only exists while something is in it, so the first hunk shifts the whole file two columns right and undo shifts it back — text that jitters sideways as you edit. Reserving it costs two columns permanently and never moves.
  - **`diffopt+=linematch:60`** is set alongside it — neovim's own diff refinement, off by default. Without it, a line with one word changed renders as a whole line deleted plus a whole line added. It improves every diff nvim draws, gitsigns' previews included.
- **diffview** — [diffview.nvim](https://github.com/sindrets/diffview.nvim), the other half of "show me the diff": what changed across the working tree, a commit, or a branch — the question the gutter can't answer because the answer spans files. File panel on the left, two-pane diff on the right, in its own tab.
  - In nvim rather than a TUI in another tmux window for one reason: reviewing isn't read-only. Half of "what did that change" ends in staging the hunk, jumping to a definition, or fixing it there and then — and in here `<leader>gs`, `gd` and the rest are all still under the hand. It also uses *neovim's own* diff engine, so `linematch:60` applies and a one-word change renders as a one-word change.
  - `<leader>gg` in and out on one key — three states, the same shape as the dap-ui panes and tmux's `<prefix>C`: looking at it closes it, open in another tab jumps to it, otherwise opens. Diffview lives in its own tab, so without the middle case a second press would silently stack a second review tab rather than returning you to the first.
  - `<leader>gm` reviews the whole branch against the default branch. The base is asked of the repo (`origin/HEAD`, falling back to probing `origin/main`/`origin/master`) rather than assumed, and the range is `base...HEAD` with **three** dots — that diffs against the merge base, so commits that landed on main after you branched don't show up as your changes. Two dots would include them and make a week-old branch unreadable.
  - **Any of these four keys closes the view from inside it**, whichever one opened it — so you never have to remember which are toggles, or fall back to `:DiffviewClose` because the key you reached for did nothing. `gf` on a row is the other way out: it leaves the review and opens the real file at that line.
  - `<leader>gh` this file's history, `<leader>gH` the repo's, and in visual mode `<leader>gh` gives the history of just the *selected lines* — `git log -L`, the "who last touched this function" query that's unusable on the command line.
  - Inside the view: `<Tab>`/`<S-Tab>` next/previous file, `-` stage or unstage the file under the cursor, `S`/`U` stage/unstage all, `X` restore it, `gf` open the real file, `g?` full keymap. Note `<leader>e` is *focus the file panel* in here rather than neo-tree — diffview's buffer-local mapping wins, which is the more useful meaning in a review.
- **LSP** — [mason.nvim](https://github.com/williamboman/mason.nvim) installs language servers, wired to `nvim-lspconfig` via `mason-lspconfig`. `lua_ls` is auto-installed; add more via `ensure_installed` or `:Mason`. Requires nvim 0.11+ (uses the `vim.lsp.config`/`vim.lsp.enable` API).
  - Keymaps (buffer-local, on attach): `gd` definition and `gr` references (routed through telescope for preview + fuzzy filter), `K` hover — and the *value* under the cursor while a debug session is stopped (see **Inspecting** below), `<leader>rn` rename, `<leader>ca` code action, `[d`/`]d` prev/next diagnostic (floats the message on jump).
- **Autocompletion** — [nvim-cmp](https://github.com/hrsh7th/nvim-cmp) with LSP, buffer, and path sources, plus LuaSnip for snippets. `<Tab>`/`<S-Tab>` cycle items and jump snippets, `<CR>` confirms, `<C-Space>` triggers completion, `<C-f>`/`<C-b>` scroll docs.
- **Copilot** — [copilot.lua](https://github.com/zbirenbaum/copilot.lua), as **ghost text only, never a cmp source**. Mixing them makes both worse: AI entries push real LSP completions out of the list, cmp's fuzzy matching fights multi-line suggestions, and you lose the ability to tell a guess from a fact. The LSP *knows* the method exists; Copilot thinks it probably does. Different keys, different colour. `hide_during_completion` (the plugin's own default) suppresses ghost text while the cmp menu is open, so the two never draw over each other.
  - `<M-y>` accept, `<M-w>` accept just the next word, `<M-]>`/`<M-[>` cycle, `<C-]>` dismiss, `<leader>ct` toggle for this buffer. `<Tab>` is untouched and still cmp/LuaSnip.
  - **Why not the usual keys** — Copilot's default accept is `<M-l>`, which *cannot* work here: tmux binds `M-l` to `select-pane -R` with `bind -n`, so tmux eats it and nvim never sees the key. Same for `<M-Right>`/`<M-Down>`, the usual accept-word and accept-line. `<Tab>` is cmp's and `<C-y>` is cmp's confirm via `preset.insert`, which leaves `<M-y>`.
  - **Filetype exclusions only** — `gitcommit`, `gitrebase`, `dotenv` and the dap repl. It runs in every repo. `:CopilotWhy` names the rule when it isn't live in a buffer; `:Copilot status` only says *that* it isn't.
  - **Node** — copilot.lua requires node ≥ 22 and errors out on anything older. nvm keeps several versions side by side and only puts one on PATH, so the usable binary is often installed and simply not active. `init.lua` uses PATH's node when it's new enough and otherwise finds the newest nvm version that is, pointing *only* Copilot at it — switching the nvm default to satisfy an editor plugin would change the node every other tool on the box runs.
  - Ghost text is `Comment` + italic. It shouldn't look like code you wrote, and tokyonight's comment colour alone is close enough to the foreground that a suggestion reads as real.
- **Debugging (DAP)** — [nvim-dap](https://github.com/mfussenegger/nvim-dap) speaks the same wire protocol VS Code's debugger does, against the same `debugpy` adapter, so breakpoints, stepping and inspection behave identically. What VS Code adds on top is the UI, which [nvim-dap-ui](https://github.com/rcarriga/nvim-dap-ui) supplies (scopes, stacks, breakpoints, watches, repl); `nvim-dap-virtual-text` prints values inline beside the code as you step. Adapters are installed by [mason-nvim-dap](https://github.com/jay-babu/mason-nvim-dap.nvim) the way mason installs servers, and the python configurations come from [nvim-dap-python](https://github.com/mfussenegger/nvim-dap-python).
  - **Running without debugging** — `<leader>mm` is the same Makefile picker without `DEBUG=1` and without attaching: the target just runs in a terminal split. That's the common case, and it avoids paying tracing overhead for a run you aren't stepping through. (`:term <cmd>` and `:!<cmd>` cover anything that isn't a make target.)
  - **Two ways in.** `<F5>` picks a configuration — in a project with a `.vscode/launch.json`, that file's configurations are in the list automatically, so VS Code's Run-and-Debug dropdown and this picker are the same list. `<leader>dM` picks a **Makefile target** instead, runs it with `DEBUG=1` in a terminal split and attaches, so the parameters live in the Makefile rather than in a second copy of the arguments. It needs the target to honour `DEBUG=1` by running behind `python -m debugpy --listen $(PORT) --wait-for-client`; the port is read out of the Makefile.
  - **Breakpoints** — `<leader>db` toggle, `<leader>dB` conditional (a python expression evaluated in the frame), `<leader>dp` logpoint (prints, never stops; `{}` interpolates), `<leader>dx` clear all.
  - **Stepping** — `<leader>dl`/`<leader>dj`/`<leader>dk` step over/into/out, with the call stack drawn vertically: callees below, callers above, execution running left to right along the line. `<leader>dK`/`<leader>dJ` are the same directions with nothing executed — they move which frame you're *looking* at. `<F10>`/`<F11>`/`<S-F11>` do the same as VS Code's keys (`<F12>` is an unshifted step-out fallback). `<leader>dc` continue, `<leader>dC` run to cursor, `<leader>dR` re-run the last configuration, `<leader>dm` debug the test the cursor is inside. Stepping is *also* on `<C-l>`/`<C-j>`/`<C-k>` — the same three moves on one keystroke, live from **any** window including the dap-ui panes, so a step you think of while reading the scopes pane doesn't cost a trip back to the code first. Nothing is shadowed: with no session stopped each key does what it always did, so `<C-l>` still redraws and clears the search highlight.
  - **Inspecting** — `K` is the everyday one: hover docs normally, and the *value* under the cursor while a session is stopped. At a breakpoint that's the question you actually have, and it's the key your hands already reach for; the docs are back the moment the session ends. `<leader>de` is the same evaluation asked for explicitly, and the one that works over a visual *selection*. `<leader>dr` a real repl in the stopped frame; `<leader>du` toggle the panes. `<leader>dD` sends the dataframe under the cursor (or the visual selection) to **VisiData**, covered below.
  - **Watches, without leaving the code** — `<leader>da` watches the expression under the cursor, taking the whole dotted name (`self.cache`, not just `cache`), or the *selection* in visual mode for what that can't reach (`rows[i]["price"]`, a slice, a call). The cursor doesn't move and the pane isn't focused — the value simply appears in the sidebar, so watching six things costs six keystrokes rather than six round trips. It works before a session starts too, since dap-ui keeps watches across sessions: line them all up, then hit `<F5>`. `<leader>dA` prompts for an expression that's nowhere in the file (`len(self.pending)`), and `<leader>dX` clears the lot — which matters precisely because watches outlive the session that made them. `<leader>dW` is still the way in to *type* one in the pane.
  - **Getting around a stopped session** — the cost worth removing is the window round-trip. `<Esc>` in any dap-ui pane or the repl goes back to the code; it *finds* the source window rather than using `wincmd p`, which is wrong the moment you've hopped between two panes. `<leader>ds` scopes, `<leader>dS` stacks and `<leader>dw` watches each toggle in **and** out on the same key; `<leader>dd` does the same without naming one, landing you in whichever pane you were last in. Once you are in the sidebar, `<Tab>` and `<S-Tab>` cycle between the panes in screen order, repl included, so the breakpoints pane needs no key of its own and `<C-w>` never enters the loop. It has to be `<Tab>` rather than `<C-h>`/`<C-j>`/`<C-k>`/`<C-l>`: three of those four are stepping commands. `<leader>df` snaps the cursor back to the line the program is stopped on, from wherever reading the code took you; `<leader>dL` puts every breakpoint in the quickfix list so `:cnext` walks them.
  - **Inline values, kept small** — `nvim-dap-virtual-text` prints each variable's value beside the code that produced it, which is what makes a stopped frame readable without opening the scopes pane at all. Two defaults are overridden, both about space. `virt_text_pos` is forced to `eol`: on nvim 0.10+ the plugin defaults to `inline`, which *inserts* the value into the line and pushes your code rightwards, so a dict with six keys can shove the end of a statement off screen — `eol` parks values past the end of the line, in space that was empty anyway, and the code never moves. And values are truncated to 40 characters, because a repr is however long the object is (a dataframe row, a list of 500 floats) and untruncated it stops being a hint and becomes the line.
  - Truncation cuts in *characters*, not bytes, so it can't split a codepoint and leave an orphaned lead byte rendering as `<c3>`. The full value is never more than one key away — `K` on the variable, `<leader>de` over a selection, `<leader>da` to pin it in the watches pane — so the virtual text only has to be enough to *recognise* a value, not read it. `<leader>dv` expands every value to full length and collapses again; `<leader>dV` turns the virtual text off entirely.
  - **Layout** — left sidebar only (scopes / breakpoints / stacks / watches). dap-ui's default bottom drawer is dropped: its `console` element never receives anything here, since every configuration runs with `console = "integratedTerminal"` and so sends program output to a terminal buffer, and the repl beside it is a `<leader>dr` away when wanted. The winbar play/step buttons are off too — every one has a keymap.
  - **Stopping where it broke** — `dap.defaults.python.exception_breakpoints` is set to `uncaught`, so a traceback halts the program *on the throwing line* with the frame still live, which is what VS Code does when a run blows up. nvim-dap asks for `default` filters otherwise, and debugpy's default is to break on nothing — so without this the session just ends and you read the traceback after the locals are gone. `raised` is deliberately not on: it stops on every exception including the ones libraries throw and swallow (a `StopIteration` per loop, a `KeyError` inside `dict.get`), which is unusable with pandas underneath. `<leader>dE` cycles `uncaught` → `raised + uncaught` → `none` mid-session, for finding an exception something upstream is catching.
  - **`<leader>re`** — the same idea for a run that *isn't* under the debugger. `<leader>rr` and `<leader>mm` leave a traceback as dead text in the terminal split, and `gf` can't follow it because `File "x.py", line 42` isn't a format vim knows. This turns the last traceback into a quickfix list and puts the cursor on the innermost frame. It joins the buffer lines before parsing, because a terminal hard-wraps at pane width and splits long paths mid-token — line-by-line matching misses any path longer than the split is wide, which in a nine-row 80-column pane is most of them.
  - **Ending** — `<leader>dt` terminates, which for debugpy is a hard kill rather than a `Ctrl-C` (no `KeyboardInterrupt`, no `finally` blocks — interrupt the terminal split instead if the run should wind down cleanly). `<leader>dq` (or `:DebugCleanup`) also closes the panes, the repl and the `<leader>dM` split; breakpoints survive it.
  - **`launch.json` caveat** — nvim's JSON parser is stricter than VS Code's. Trailing commas, and `//` comments sharing a line with code, make the whole file unparseable and nvim-dap falls back silently to the generic configurations. Keep comments on their own line.
  - **Which python runs your code** — `$VIRTUAL_ENV`, else `$CONDA_PREFIX`, else the first `venv`/`.venv`/`env`/`.env` directory under the cwd or an attached LSP's root. `debugpy` does *not* need installing into that venv: the adapter injects its own copy onto the debuggee's `sys.path`, which is how the VS Code extension gets away with bundling one debugpy for every project.
- **Auto-reload on external edits** — a buffer changed by something else (claude in another tmux pane, a `git checkout`, a formatter) reloads on focus, buffer entry, or 250ms idle, with a notification so it never changes silently under the cursor. `autoread` alone is not enough: it only re-reads when something prompts nvim to look, and `:checktime` is that prompt. Two non-obvious parts — tmux needs `focus-events on` or `FocusGained` never fires under it at all, and `:checktime` must be `vim.schedule`d because calling it straight from an autocmd callback is silently ignored under textlock.
- Leader is `<Space>`; `jk` escapes insert mode; `M-u`/`M-d` alias `C-u`/`C-d` so the same keys half-page-scroll nvim, tmux copy mode and the Claude TUI; 2-space indentation, no swapfile.
- **`scrolloff = 8`** — 8 lines of context kept above and below the cursor. This does more for how scrolling *feels* than any animation setting: at 0 the view only moves once the cursor hits the edge, so reading down a file is a series of lurches; at 8 the window slides continuously. `smoothscroll` is on too, so wrapped long lines scroll by screen row instead of snapping in and out whole.
- **Hybrid line numbers** (`number` + `relativenumber`) — the cursor line shows its absolute number, every other line shows its distance. That gutter is what makes counted jumps (`7j`, `d2j`) aimable: read the number, type it.
- **`tutorial.rs`** — the practice range. A tier-ordered walkthrough for becoming a power user, drilled against real Rust code sitting in the file. Each section explains the idea, then gives `TRY IT` exercises with concrete targets ("cursor anywhere in `timeout_ms`, press `ciw`, type `deadline_ms`"). Open it, work top to bottom, wreck the code, and reset with `:e!` — that's a repeatable 10-minute daily loop.
  - Order is deliberate — grammar before plugins: motions → **text objects** → `.` → counts → insert → registers → visual/blockwise → macros → `:s`/`:g` → marks → telescope → harpoon → LSP → cmp. Tiers 1-4 are where the speed actually lives; plugins add capability but don't compound the way `ciw` does.
  - It also explains *how to think* in vim (vim is a language, not a set of shortcuts) and how the rest of these dotfiles feed the editing loop.
  - The LSP section needs `rust-analyzer` (`:Mason`, press `i` on it); `lua_ls` is the only server auto-installed.
- **`drills.py`** — the speed course. Where `tutorial.rs` explains and `motions.lua` reference, this is nine sessions of *drills with pass marks*: land on any character in ≤2 keys, change any argument from anywhere inside it, rename with `cgn` + `.` without typing the word twice, comment a ragged block with `<C-q>`, turn raw rows into dicts with one recorded macro. Ten minutes a day, one session, repeated until the pass mark is dull rather than possible. Ends with a graduation checklist. Practice material is Python, since that's what the working day is.
  - Its three rules matter more than any key in it: never press `hjkl` twice in a row; let the *distance* to the target pick the tool (`f`/`t` on the line, `s` on screen, `/` or a count in the file, telescope between files); and count keystrokes, because speed is pressing fewer keys rather than typing faster.
- `motions.lua` is the companion cheat-sheet for getting around a file.

### tmux (`tmux/.tmux.conf`)
- Prefix rebound to `C-Space`; mouse on; windows/panes start at 1 and renumber; 10,000 lines of scrollback per pane.
- `focus-events on` — off by default, and its absence is why nvim's `autoread` looks broken under tmux: `FocusGained` never arrives, so a buffer edited in another pane stays stale. See the nvim auto-reload note above.
- Split with `|` / `-`, resize with `prefix H/J/K/L`, reload with `prefix r`.
- **Pane hopping, zoom-preserving** — `M-h/j/k/l` (or `M-<arrow>`) moves between panes with no prefix at all, and `M-1`…`M-5` jumps straight to a pane by number *and zooms it*. `M-z` toggles zoom. Every move uses `select-pane -Z`, which "keeps the window zoomed if it was zoomed" — so once you're full screen you stay full screen while moving around, instead of dropping back to the split layout and having to zoom again. `prefix h/j/k/l` still works and is zoom-preserving too.
  - `bind -n` takes those keys from whatever runs inside the pane. Checked against this setup: zsh is in vi mode, where the only Alt bindings are `M-,` `M-/` `M-c` `M-~`, so none of these collide; nvim uses `<C-w>` for its own splits and is unaffected.
- **Windows for anything long-lived** — `M-H`/`M-L` move between windows, `prefix ;` is last-window. Programs drawing into the terminal's *normal* buffer (a shell) don't re-anchor their output when the pane changes size, so zooming or splitting leaves them mispositioned and you end up scrolling to find the content. Full-screen programs on the *alternate* buffer (nvim, less, htop, claude) repaint instead, but still have to re-render everything on each resize. A window is always the full terminal size, so switching windows resizes nothing — put claude and long-running jobs in their own window and the problem disappears; keep panes for short-lived shells you want side by side.
- **Scrolling without the mouse** — `M-u` drops into copy mode already scrolled up a page and `M-d` pages back down (both repeat while Alt is held; `Shift+PageUp` does the same for a docked full keyboard, but on a laptop PageUp is `Fn+Up` and not worth the stretch). Inside copy mode `C-u`/`C-d` still give half pages, and it's vim inside: `k`/`j`, `C-u`/`C-d`, `C-b`/`C-f`, `g`/`G` for the ends of the history, `/` to search with `n`/`N`, `q` to leave. `prefix [` is the long way in. Only shells have scrollback worth this, so the bindings are guarded on `#{alternate_on}`: a program on the *alternate* screen (claude, nvim, less) keeps its own history and writes nothing to tmux's, so copy mode there would show only the stale shell output from before it started — a few dozen lines that stop dead and look like a broken scroll limit. In those panes the key is forwarded to the program and scrolling is the program's own job. `mode-keys` is set to `vi` explicitly rather than left to tmux's inference from `$EDITOR`.
  - Selection inside copy mode keeps tmux's defaults, which differ from vim: `Space` starts a selection (`v` is block-select), `Enter` copies and exits.
- Tokyo Night status bar; true colour; 10ms escape-time to avoid WezTerm garbage.

### wezterm (`wezterm/.wezterm.lua`)
- JetBrains Mono, rose-pine-moon, acrylic-blurred transparent window.
- Bottom tab bar, blinking bar cursor, 10k scrollback.
- **Dictating into a terminal (Wispr Flow)** — works directly: dictate and the text lands in the focused pane. It needs `use_ime = true` below, and nothing else; no copy-then-paste dance.
  - Why it needs that: Flow injects **synthesised character input**, not keystrokes. Capturing the tty with `cat -v` during a dictation caught *zero bytes* in WezTerm while manual typing in the same capture came through fine — and the identical capture in Windows Terminal caught the plain literal characters. WezTerm reads the keyboard through the raw-input path, where posted character messages never appear.
  - Flow also puts each transcript on the clipboard and **restores the previous contents ~455ms later** (polled at 60ms: set `18:31:58.171`, reverted `18:31:58.626`). That's why every clipboard-based workaround loses the race, and why `Shift+Alt+Z` and manual `Ctrl+V` both fail — they aren't needed now, but it explains the dead ends if you go looking.
  - Claude Code's own `/voice` is the alternative: it records inside WSL via SoX/PulseAudio, with no Windows text injection in the path at all.
- `use_ime = true` — **required for dictation** (Wispr Flow) and text expanders to reach the terminal. They inject text as synthesised character input, not keystrokes: measured, Flow's output arrives in Windows Terminal as plain literal characters and in WezTerm, without this, as nothing at all. WezTerm reads the keyboard through the raw-input path where posted character messages never appear; the IME path is the other way in.
- `Ctrl+V` pastes. WezTerm binds `Ctrl+Shift+V` and leaves unshifted `Ctrl+V` to pass through to the program — where Claude Code takes it as `chat:imagePaste` and hunts the clipboard for an *image*, so a text paste silently does nothing. Cost: nvim no longer sees `<C-v>`; press `<C-q>` for blockwise visual, which vim treats identically.
- **Restart WezTerm after editing this file** — don't trust hot-reload. `use_ime` only applies at window creation, and the stub's reload watch sits on a `\\wsl.localhost` path, where Windows change notifications are unreliable. Several apparent "this fix doesn't work" results were really a config that had never loaded.
- `Shift+PageUp`/`Shift+PageDown` are forwarded rather than scrolling WezTerm's own scrollback — with tmux running that buffer holds stale repainted frames, not session output, so the keys belong to tmux's copy mode.
- Boots straight into WSL + a tmux session named `main`.
- WezTerm runs on Windows and can't follow WSL symlinks, so `install.sh` writes a
  tiny Windows-side stub that live-loads this file over the `\\wsl.localhost` path
  (edits hot-reload; no re-copy needed).

### claude (`claude/`)
Global [Claude Code](https://claude.com/claude-code) config:
- `settings.json` — model, notification/stop sound hooks (Windows), enabled plugins, and the status line command.
- `CLAUDE.md` — global instructions, loaded into every session in every directory. Currently: maths notation, routed by destination — Unicode glyphs (∫, Σ, x̄) in terminal replies since LaTeX source is unreadable there, and real LaTeX (`$…$`) in `.md`/`.tex`/`.ipynb` files, which get read through a renderer.
- `keybindings.json` — laptop-friendly scrolling. `settings.json` sets `"tui": "fullscreen"`, where the conversation is a scrollable view whose only default scroll keys are `pageup`/`pagedown` — which a laptop reaches through `Fn`. These add vim keys on Alt: `M-u`/`M-d` half page, `M-b`/`M-f` full page, `M-g`/`M-G` top/bottom (the file itself spells them `alt+u`, `alt+shift+g` and so on — Claude's own syntax, not tmux's `M-` shorthand). Alt was chosen because Claude's own bindings use `alt+p/o/t/w/v` and tmux's use `M-h/j/k/l`, `M-z`, `M-1`–`M-5`, `M-H/M-L` — no overlap — and because tmux forwards `M-u`/`M-d` into alternate-screen panes rather than swallowing them.
- `statusline-command.sh` — custom status line showing model, effort, context %, cost, rate limits, and git state (needs `jq`).

### visidata (`visidata/.visidatarc`)
- **[VisiData](https://visidata.org)** — the terminal spreadsheet, and the answer to "where's VS Code's Data Viewer". Sort (`[`/`]`), filter (`|`/`\`), frequency tables (`Shift+F`), summary stats (`Shift+I`), on CSV/TSV/JSON/parquet/SQLite. `Ctrl+R` reloads the file, which is what makes it usable mid-debug.
- **The workflow it exists for** — at a breakpoint, `<leader>dD` over a dataframe. It evaluates `df.to_csv('/tmp/peek.csv', index=False)` in the stopped frame and opens `vd` on the file in its own tab, which is the two steps below on one key. By hand: dump the frame from the DAP repl (`<leader>dr`) with `df.to_csv('/tmp/peek.csv', index=False)`, then `vd /tmp/peek.csv` in a tmux window. The debug session stays stopped throughout: the repl evaluates *in* the stopped frame, so `df` is already in scope, and writing a file doesn't resume anything. Step, re-dump, `Ctrl+R`. It's a snapshot rather than a live view — so is VS Code's. A second `<leader>dD` rewrites the file and jumps to the vd already open on it rather than starting a new one, so the reload keeps the sorts, selections and cursor you had set up.
- `install.sh` installs it with `uv tool install` rather than pip: it only ever *reads* a file, so it has no business in a project venv, and uv gives it a private one and links just the binary into `~/.local/bin`. Which is why `<leader>dD` shells out to `vd` instead of importing visidata: it is not importable from the project interpreter, and the debuggee's stdout is a dap terminal buffer rather than a tty, so an in-process viewer would have nothing to draw on.
- **The one setting worth overriding** — `disp_float_fmt`. VisiData's default is `{:.2f}`, which renders a probability of `0.0034` as `0.00` and a coefficient of `-0.000181` as `-0.00`: not rounded, but indistinguishable from zero and from each other, with nothing on screen to say so. `{:.6g}` is six *significant figures* rather than decimal places, so precision follows magnitude — `0.0034` stays itself and `1400.0` shortens to `1400`.
- Nothing else is set. VisiData detects WSL on its own and already points `clipboard_copy_cmd` at `clip.exe`.

## Install

```sh
git clone <this-repo> ~/dotfiles
cd ~/dotfiles
./install.sh
```

`install.sh` is safe to re-run. It:
- symlinks each config into place, backing up any existing real file to `*.bak`;
- checks for the required tools and prints an install command for your package manager if any are missing;
- sets zsh as your default shell (`chsh`);
- on WSL, writes the Windows-side WezTerm stub — and skips that step everywhere else.

Then reload with `exec zsh` (or `source ~/.zshrc`).
